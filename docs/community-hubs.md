# Community Hubs schedule

The 14 Devcon 8 Community Hubs run their own programme and are not in Pretalx. Each hub fills in a shared spreadsheet template on dSheets (sheets.fileverse.io); devcon-api reads those sheets live (cached in memory) and serves them as their own schedule bundle, which the event app shows through its normal schedule view as a separate dataset. Nothing is written to `data/` and the hub sessions never mix with the Pretalx schedule.

## The template

One tab per event day, named by weekday and date ("Tue 3", "Wed 4", ...; the month is implied), plus an "Info" tab the hub fills freely (only the "Hub name" cell is read) and a "Read me" tab with instructions and an example. Each day tab shows the hub's name and the day at the top, a spot for the hub's logo, and one row per session: Time from / to (dropdowns, 08:00 to 22:00 in 15-minute steps, Mumbai time), Session title, Format (dropdown), Speaker(s) (comma separated), Description (optional). The time options live in a hidden column (AJ) far to the right of each day tab, because dSheets keeps hidden columns but not hidden tabs on import, and hubs may add their own columns next to the schedule.

Each hub has a colour (a strong tone for the sheet headers, the matching pastel for its badge and cards in the app; same values in `devcon-api/src/utils/community-hubs.ts` and `event-app/src/data/communityHubs.ts`). Hubs that want to colour rows by topic do it by hand in dSheets: its importer keeps cell fills but drops formula-based conditional formatting, so a "colour the row from a Topic column" rule cannot ship in the template until Fileverse maps such rules to the engine's `formula` condition (which it does support).

The day of a row comes from its tab name (anything the day parser understands: "Wed 4", "Day 2", a full date), so tab order is free: dSheets opens the first tab, and hubs drag today's tab to the front each morning so the embedded sheet opens on the current day. A "Day N" banner row inside a tab still overrides the tab's day, and the earlier single-tab layouts (banner blocks, or a Day column per row) still parse.

Rows the sync cannot read are skipped and reported per tab (missing title, no day, unparseable time, end before start). Times are also accepted typed as `9:00`, `09.30`, `9h30`, `2:30 pm` or `1430`; a tab name, banner or Day column as `Day 2`, a weekday, `4 Nov` or an ISO date.

The template is generated by `scripts/build_template.py` style openpyxl code kept outside the repo; note that dSheets imports through ExcelJS, which rejects openpyxl's default output (absolute relationship targets, unprefixed drawing XML). The generator post-processes the zip to fix both.

## Reading a dSheet

Fileverse has no read API. The app fetches sheet metadata from a public indexer, downloads the encrypted workbook from IPFS and decrypts it in the browser with the key in the share link (`#k=`). `devcon-api/src/clients/fileverse.ts` does the same server side (secretbox, PBKDF2 and AES-CBC to unwrap the file key, AES-GCM on the content, gzip, then a Yjs document holding the cells). It reads the last version the owner's browser published, which lags live edits by minutes at most.

Writing to a dSheet programmatically is not practical (realtime socket with owner tokens), so the sync is read only.

## The API

`devcon-api/src/services/community-hubs.ts` reads every configured hub sheet, parses it and keeps the result in memory for two minutes (concurrent requests share one refresh). What is served is always the last good read of each hub:

- a sheet that cannot be read or has lost its header row keeps its previous read in service
- a fresh read that parses with problems and yields fewer sessions than the served one (a banner or time cell typed over) is held back; additive edits with one bad row go live with the bad row reported
- the status endpoint says per hub whether the latest or the previous read is served and lists the problems to fix

The parsed sheets are also written to one file per event, `devcon-api/data/community-hubs/<eventId>.json`, which seeds the cache after a restart and covers a Fileverse outage. In production the API commits that file to the repo (`[skip deploy]`, at most every 30 minutes and only when the served version changed) so a redeploy also starts from the last good sheets. Three endpoints, all CDN-cached for 60 s like the event endpoints:

- `GET /events/:id/community-hubs` status: which hubs were read, when they last published, rows that could not be parsed
- `GET /events/:id/community-hubs/version` changes when any hub publishes or the hub set changes
- `GET /events/:id/community-hubs/bundle` sessions, speakers and rooms in the offline bundle shape: one room `community-hub-<id>` per hub, `track: "Community Hubs"`, `type` = Format, `tags: [hub name]`, times converted from the event's city (Mumbai; Bangkok when the event is `devcon-7`, which the test sheets target)

Configuration is the `COMMUNITY_HUB_SHEETS` env var on the API: a JSON object of hub id to share link, e.g. `{"privacy":"https://sheets.fileverse.io/sheet/<id>#k=<key>"}`. Hub ids and names are hardcoded in `devcon-api/src/utils/community-hubs.ts`. The link key grants access to the sheet (edit access when the hub shares an editable link), so the links stay out of the repo.

## In the app

The hubs' programme lives in a second store (`event-app/src/data/store/hub-store.ts`, fed by `communityHubsDataset(...)` in `dataset.ts`, rows keyed under `<event>-community-hubs`) and never mixes with the Pretalx schedule. The Schedule tab has a "Programme / Community Hubs" segment: every data hook under it reads the store the segment selects (`schedule-source.tsx`), so list, timeline, filters and cards work unchanged. The list or timeline view carries over the switch (the timeline shows one column per hub); the Filter sheet's Rooms section narrows to one hub. My Interests spans both programmes: while it is on, the list shows every starred session from the Pretalx schedule and the hubs together, and the switch gives way to a note saying so. The segment is reflected in the URL as `/schedule?hubs=1` (home card, deep links), switching is client side, and the other tabs are unaffected. Hub session pages show a link to the hub's sheet instead of Q&A, and no recording or livestream slot; hub speakers resolve from the hub store on both segments. Hub sessions carry their hub's logo where Pretalx tracks show gem artwork (cards, timeline, details banner): `event-app/public/community-hubs/logos/<hub id>.svg`, placeholders until a hub sends its own, replaced in place under the same name. For devcon-7 the hub dataset reads a static snapshot under `public/community-hubs/` until the endpoint is deployed.

`/community-hubs` embeds each hub's dSheet directly (`?embed=1` hides the dSheets chrome), the way the Devconnect 2025 site did, and is linked from the home card and from hub session pages. Embedded links must be view or comment links: whoever opens the page can open them.
