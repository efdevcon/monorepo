# Community Hubs schedule

The 14 Devcon 8 Community Hubs run their own programme and are not in Pretalx. Three community-run spaces use the same template and pipeline as if they were hubs: Open Hardware Zone, Game Zone and Music Stage (2026-10-27; Music Stage moved out of Pretalx, its sheet pre-filled from the Pretalx slots of 21 Oct). Each hub fills in a shared spreadsheet template on dSheets (sheets.fileverse.io); devcon-api reads those sheets live (cached in memory) and serves them as their own schedule bundle, which the event app shows through its normal schedule view as a separate dataset. Nothing is written to `data/` and the hub sessions never mix with the Pretalx schedule.

## The template

One sheet, "Schedule" (v5, 2026-10-07). Row 1: hub name (identifies the sheet; the app shows the name from the hub registry) and a link to the shared Read me, a separate dDoc. Then one row per session: `ID`, `Day`, `From`, `To`, `Session title`, `Format (optional)`, `Speaker(s)`, `Description (optional)`, `Topic (optional)`. Day, times, Format and Topic are dropdowns (strict once imported, dSheets prohibits other input on any list validation); Format and Topic ship with starter lists that hubs edit in dSheets (Data validation). Time options (09:00 to 18:30 in 10-minute steps) sit in column K under the schedule rows, headed "Times for From/To: add more below" (row 105, list from row 106), followed by 20 empty cells that already belong to the dropdown: since list input is strict, a hub that needs an off-grid time types it there. Until 2026-10-20 the list was hidden in column AJ; in rows 1 to 58 (until 2026-10-16) it shifted whenever a hub inserted, deleted or dragged schedule rows, dropping times from the dropdown. Hub sheets made from the older layout get the same fix by export, edit and re-upload. The header row carries the hub's colour. Hub names, ids and order follow the coordinator's official list (hub numbers 1 to 14, 2026-10-07).

- `ID` (pre-filled `S01`...) is the session id in the app, `<hub>-<id>`, so a retitled row keeps its stars and reminders. Whole rows must move together. Without an id the sync falls back to `<hub>-<title slug>`, and reports id-less rows and duplicate ids.
- `Topic` becomes the session's second tag (after the hub name): shown on the session, filterable in the app.
- URLs in descriptions become links; a cell link is appended to the text by the sync.
- Columns are matched by header text, the hub name by its label, so order is free. The v4 layout (one tab per day, Info and Read me tabs) still parses.

Generated by `build_v5.py`, kept outside the repo (writes the sheet XML directly; dSheets imports through ExcelJS, which rejects openpyxl output). Its `--all` mode writes the 14 hub files to `devcon/public/community-hubs-templates/<Hub-name>.xlsx`, served at devcon.org/community-hubs-templates/ with a `Content-Disposition: attachment` header (`devcon/netlify.toml`) so the link downloads. The hosted files carry the Read me doc's Fileverse link, whose key is read-only, the one share key allowed in the repo.

## Reading a dSheet

Fileverse has no read API. The app fetches sheet metadata from a public indexer, downloads the encrypted workbook from IPFS and decrypts it in the browser with the key in the share link (`#k=`). `devcon-api/src/clients/fileverse.ts` does the same server side (secretbox, PBKDF2 and AES-CBC to unwrap the file key, AES-GCM on the content, gzip, then a Yjs document holding the cells). It reads the last version the owner's browser published, which lags live edits by minutes at most.

Only the owner's browser publishes: collaborators' edits live in the realtime room until the owner opens the sheet. Since 2026-10-20 the hub sheets are owned by the Devcon team and shared "anyone with the link can edit", so the API no longer reads the published version. An hourly GitHub Action (`.github/workflows/fileverse-live-export.yml`) reads the live state instead. The API starts it at minute 7 of every hour (`startLiveExportTimer`, production only), because GitHub runs this repo's schedules hours late (the daily cleanup at 00:00 UTC fires around 04:00 to 06:00); the workflow's own cron is only a backup:

1. `.github/scripts/fileverse-live-export.mjs` opens every hub's edit link in headless Chromium (Playwright, installed in /tmp, outside the workspace), answers the display-name prompt as "Devcon bot (read-only)", and dumps the Yjs updates the editor stores in IndexedDB under the sheet id. An edit link carries the room key, which is why only "anyone with the link can edit" sheets work. Never open the IndexedDB before the editor has created it (an empty v1 database breaks the editor).
2. `pnpm community-hubs:live <dump dir>` (devcon-api) turns them into cells with `readTabsFromUpdates` (same cell reading as the published path) and writes `devcon-api/data/community-hubs/sheets.json`: per hub its tabs, `changedAt` (when the cells last changed) and the read error if any (a failed hub keeps its previous cells). The file is rewritten only when cells change, or every 6 hours as a heartbeat (`exportedAt`). Next to it, `devcon8-sessions.json` holds the same sheets parsed into sessions as the app shows them (id, day, time, title, format, speakers, topic, description, plus each hub's problems), without per-read timestamps, so a commit's diff reads as "this session changed". The API does not read it.
3. The workflow commits it with `[skip deploy]`, so Render does not redeploy.

The links live only in the Action's `COMMUNITY_HUB_SHEETS` secret (JSON object of hub id to edit link). Anyone holding a link can edit that sheet: the export never logs them and the file holds cells only. Failed reads leave a screenshot artifact (3 days).

Writing to a dSheet programmatically is not practical (realtime socket with owner tokens), so the sync is read only.

## The API

`devcon-api/src/services/community-hubs.ts` reads `sheets.json` from GitHub (contents API on `main`, not CDN-cached; the deployed copy is only the fallback, since the export's commits skip deploys), parses every hub in it and keeps the result in memory for two minutes (concurrent requests share one refresh). A hub's `changedAt` is served as its publish time, so the version the app polls changes only when cells change. The status endpoint reports `exportedAt` and flags an export older than 8 hours. What is served is always the last good read of each hub:

- a sheet that cannot be read or has lost its header row keeps its previous read in service
- a fresh read that parses with problems and lost a large share of the served sessions (more than 3 and more than a quarter: a column typed over) is held back; anything smaller (a title cleared, a time missing) goes live with the bad rows reported
- the status endpoint says per hub whether the latest or the previous read is served and lists the problems to fix

The parsed result lives in memory only. After a restart, and while GitHub is unreachable, the API serves the copy of `sheets.json` that shipped with the deploy; it writes nothing back to the repo (until 2026-10-20 it committed its own per-event cache, `data/community-hubs/<eventId>.json`, which only added timestamp noise once the export existed). Three endpoints, all CDN-cached for 60 s like the event endpoints:

- `GET /events/:id/community-hubs` status: which hubs were read, when they last published, rows that could not be parsed
- `GET /events/:id/community-hubs/version` changes when any hub publishes or the hub set changes
- `GET /events/:id/community-hubs/bundle` sessions, speakers and rooms in the offline bundle shape: one room `community-hub-<id>` per hub, `track: "Community Hubs"`, `type` = Format (blank when the row has none; rows with Format "Break" are left out, so lunch and breaks stay in the sheets but never show in the app), speakers keyed by name slug: a hub speaker whose full name (two words or more) matches a speaker of the same event's main programme reuses that speaker's photo, bio and socials, everyone else gets the shared speaker sheet's photo and socials when it lists them (below), else a generated avatar, `tags: [hub name, topic]` (the topic only when the row has one), session ids from the Key column (`<hub>-<key>`) or the title, times converted from the event's city (Mumbai; Bangkok when the event is `devcon-7`, which the test sheets target)

Configuration is the `COMMUNITY_HUB_SHEETS` GitHub Actions secret (see above), e.g. `{"privacy":"https://sheets.fileverse.io/sheet/<id>#k=<key>"}`; the API itself has no sheet links (its former env var of the same name is gone). Hub ids and names are hardcoded in `devcon-api/src/utils/community-hubs.ts`. A hub dropped from the secret drops out of `sheets.json` and the app on the next export.

## Speaker photos: the shared speaker sheet

Hub sheets name speakers only. One shared dSheet, filled by the hub leads, gives hub speakers a photo and a social link; only speakers who are not on the main programme need a row (a Devcon speaker's own profile wins). Columns matched by header text, in any order: `Name` (exactly as written in the hub sheet; matched by slug, so case and spacing don't matter), `Social` (an X or GitHub profile link), `Photo URL` (a link to the original image, or a Google Drive or Dropbox share link, which the export turns into a download; the export keeps its own copy). Either of the last two may be empty: with no photo, the X profile picture is used, else GitHub's. A `Hub` column or any other column is ignored.

- Its edit link sits in the `COMMUNITY_HUB_SHEETS` secret under the reserved id `speakers`, so the hourly export reads it like a hub sheet. The export resolves every row, mirrors the photo into the avatar bucket (the same mirror as Pretalx speaker photos: 256px webp, keyed by source URL, so an unchanged link costs one HEAD per run; `SUPABASE_URL` / `SUPABASE_KEY` in the workflow) and writes `devcon-api/data/community-hubs/speaker-photos.json`: `{ exportedAt, speakers: { <slug>: { name, avatar, twitter, github, website } }, problems }`. Rows with neither photo nor social, unreadable links, photos that could not be fetched and duplicate names are listed in `problems`, which the status endpoint (and the devcon.org monitor) show prefixed with "speaker sheet:".
- The API reads that file next to `sheets.json` (GitHub, local fallback) and applies it when building the bundle. Precedence per speaker: main-programme profile, then the sheet, then the generated avatar. The app needs nothing: `avatar`, `twitter`, `github`, `website` are the fields it already shows.
- A changed photo link is a new source URL, so it is mirrored afresh; a new picture behind the same link is not picked up (the mirror is keyed by URL).

## In the app

The hubs' programme lives in a second store (`event-app/src/data/store/hub-store.ts`, fed by `communityHubsDataset(...)` in `dataset.ts`, rows keyed under `<event>-community-hubs`) and never mixes with the Pretalx schedule. The Schedule tab has a "Tracks / Community" segment (labelled "Sessions / Community Hubs" until 2026-10-27): every data hook under it reads the store the segment selects (`schedule-source.tsx`), so list, timeline, filters and cards work unchanged. The list or timeline view carries over the switch (the timeline shows one column per hub); the Filter sheet's Rooms section narrows to one hub. My Interests spans both programmes: while it is on, the list shows every starred session from the Pretalx schedule and the hubs together, and the switch gives way to a note saying so. The segment is reflected in the URL as `/schedule?hubs=1` (home card, deep links), switching is client side, and the other tabs are unaffected. Hub session pages have no Q&A, recording or livestream slot; hub speakers resolve from the hub store on both segments, and a hub speaker's own page (`/speakers/<id>`) switches to the hubs programme by itself, since the Speakers tab otherwise reads only the Pretalx one. Someone on both programmes has the same id in each (the API keys hub speakers by name slug and reuses the Pretalx speaker's photo, bio and socials): their page and panel always show the Pretalx profile and list the sessions of both programmes (`useSpeakersData` joins the other store's sessions). Stars on hub sessions earn session reminders like any other: the inbox derives them from both programmes, and the push dispatcher merges the hubs bundle into its catalogue. A row's Topic shows as a chip beside the hub badge (cards on desktop, details everywhere) and the Filter sheet's Community Hubs mode lists topics under "Topics" next to "Hubs" (`communityHubTopics` tells the two apart by hub name). URLs in any session description are clickable (`TextWithLinks`). Hub sessions carry their hub's logo where Pretalx tracks show gem artwork (cards, timeline, details banner): `event-app/public/community-hubs/logos/<hub id>.svg`, the hubs' own artwork since 2026-10-15: `<id>.svg` is the square mark (cards, timeline, filters), `<id>-lockup.svg` the mark-plus-wordmark lockup for the session details banner (`communityHubLockup`), both run through svgo; India sent PNGs only (`india.png`, `india-lockup.png`). For devcon-7 the hub dataset reads a static snapshot under `public/community-hubs/` until the endpoint is deployed.
