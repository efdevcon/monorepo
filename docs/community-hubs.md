# Community Hubs schedule

The 14 Devcon 8 Community Hubs run their own programme and are not in Pretalx. Each hub fills in a shared spreadsheet template on dSheets (sheets.fileverse.io); devcon-api reads those sheets live (cached in memory) and serves them as their own schedule bundle, which the event app shows through its normal schedule view as a separate dataset. Nothing is written to `data/` and the hub sessions never mix with the Pretalx schedule.

## The template

One sheet, "Schedule" (v5, 2026-10-07). Row 1: hub name (identifies the sheet; the app shows the name from the hub registry) and a link to the shared Read me, a separate dDoc. Then one row per session: `ID`, `Day`, `From`, `To`, `Session title`, `Format (optional)`, `Speaker(s)`, `Description (optional)`, `Topic (optional)`. Day, times, Format and Topic are dropdowns (strict once imported, dSheets prohibits other input on any list validation); Format and Topic ship with starter lists that hubs edit in dSheets (Data validation). Time options (09:00 to 18:30 in 10-minute steps) sit hidden in column AJ. The header row carries the hub's colour. Hub names, ids and order follow the coordinator's official list (hub numbers 1 to 14, 2026-10-07).

- `ID` (pre-filled `S01`...) is the session id in the app, `<hub>-<id>`, so a retitled row keeps its stars and reminders. Whole rows must move together. Without an id the sync falls back to `<hub>-<title slug>`, and reports id-less rows and duplicate ids.
- `Topic` becomes the session's second tag (after the hub name): shown on the session, filterable in the app.
- URLs in descriptions become links; a cell link is appended to the text by the sync.
- Columns are matched by header text, the hub name by its label, so order is free. The v4 layout (one tab per day, Info and Read me tabs) still parses.

Generated by `build_v5.py`, kept outside the repo (writes the sheet XML directly; dSheets imports through ExcelJS, which rejects openpyxl output). Its `--all` mode writes the 14 hub files to `devcon/public/community-hubs-templates/<Hub-name>.xlsx`, served at devcon.org/community-hubs-templates/ with a `Content-Disposition: attachment` header (`devcon/netlify.toml`) so the link downloads. The hosted files carry the Read me doc's Fileverse link, whose key is read-only, the one share key allowed in the repo.

## Reading a dSheet

Fileverse has no read API. The app fetches sheet metadata from a public indexer, downloads the encrypted workbook from IPFS and decrypts it in the browser with the key in the share link (`#k=`). `devcon-api/src/clients/fileverse.ts` does the same server side (secretbox, PBKDF2 and AES-CBC to unwrap the file key, AES-GCM on the content, gzip, then a Yjs document holding the cells). It reads the last version the owner's browser published, which lags live edits by minutes at most.

Writing to a dSheet programmatically is not practical (realtime socket with owner tokens), so the sync is read only.

## The API

`devcon-api/src/services/community-hubs.ts` reads every configured hub sheet, parses it and keeps the result in memory for two minutes (concurrent requests share one refresh). What is served is always the last good read of each hub:

- a sheet that cannot be read or has lost its header row keeps its previous read in service
- a fresh read that parses with problems and yields fewer sessions than the served one (a banner or time cell typed over) is held back; additive edits with one bad row go live with the bad row reported
- the status endpoint says per hub whether the latest or the previous read is served and lists the problems to fix

The parsed sheets are also written to one file per event, `devcon-api/data/community-hubs/<eventId>.json`, which seeds the cache after a restart and covers a Fileverse outage. In production the API commits that file to the repo (`[skip deploy]`, at most every 30 minutes and only when the served version changed) so a redeploy also starts from the last good sheets. Three endpoints, all CDN-cached for 60 s like the event endpoints:

- `GET /events/:id/community-hubs` status: which hubs were read, when they last published, rows that could not be parsed
- `GET /events/:id/community-hubs/version` changes when any hub publishes or the hub set changes
- `GET /events/:id/community-hubs/bundle` sessions, speakers and rooms in the offline bundle shape: one room `community-hub-<id>` per hub, `track: "Community Hubs"`, `type` = Format (blank when the row has none), `tags: [hub name, topic]` (the topic only when the row has one), session ids from the Key column (`<hub>-<key>`) or the title, times converted from the event's city (Mumbai; Bangkok when the event is `devcon-7`, which the test sheets target)

Configuration is the `COMMUNITY_HUB_SHEETS` env var on the API: a JSON object of hub id to share link, e.g. `{"privacy":"https://sheets.fileverse.io/sheet/<id>#k=<key>"}`. Hub ids and names are hardcoded in `devcon-api/src/utils/community-hubs.ts`. The link key grants access to the sheet (edit access when the hub shares an editable link), so the links stay out of the repo.

## In the app

The hubs' programme lives in a second store (`event-app/src/data/store/hub-store.ts`, fed by `communityHubsDataset(...)` in `dataset.ts`, rows keyed under `<event>-community-hubs`) and never mixes with the Pretalx schedule. The Schedule tab has a "Programme / Community Hubs" segment: every data hook under it reads the store the segment selects (`schedule-source.tsx`), so list, timeline, filters and cards work unchanged. The list or timeline view carries over the switch (the timeline shows one column per hub); the Filter sheet's Rooms section narrows to one hub. My Interests spans both programmes: while it is on, the list shows every starred session from the Pretalx schedule and the hubs together, and the switch gives way to a note saying so. The segment is reflected in the URL as `/schedule?hubs=1` (home card, deep links), switching is client side, and the other tabs are unaffected. Hub session pages have no Q&A, recording or livestream slot; hub speakers resolve from the hub store on both segments, and a hub speaker's own page (`/speakers/<id>`) switches to the hubs programme by itself, since the Speakers tab otherwise reads only the Pretalx one. Stars on hub sessions earn session reminders like any other: the inbox derives them from both programmes, and the push dispatcher merges the hubs bundle into its catalogue. A row's Topic shows as a chip beside the hub badge (cards on desktop, details everywhere) and the Filter sheet's Community Hubs mode lists topics under "Topics" next to "Hubs" (`communityHubTopics` tells the two apart by hub name). URLs in any session description are clickable (`TextWithLinks`). Hub sessions carry their hub's logo where Pretalx tracks show gem artwork (cards, timeline, details banner): `event-app/public/community-hubs/logos/<hub id>.svg`, placeholders until a hub sends its own, replaced in place under the same name. For devcon-7 the hub dataset reads a static snapshot under `public/community-hubs/` until the endpoint is deployed.
